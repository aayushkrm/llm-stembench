# Reproducibility Guide

Every published number regenerates from committed artifacts with the commands below.
Environment: Python ≥3.10 (developed on 3.12), dependencies in `pyproject.toml`.

## 0. Fresh checkout

```bash
git clone https://github.com/aayushkrm/llm-stembench && cd llm-stembench
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
pytest tests/ -q          # entire suite must pass offline
```

No API keys are needed for anything in this guide except §3 (re-running live models);
`.env` (gitignored) holds free-tier keys, names documented in `.env.example`.

## 1. Rebuild the benchmark (deterministic)

```bash
python -m stembench.benchmark_gen.build --out data/stembench_v1 --seed 20260817
sha256sum data/stembench_v1/items.jsonl   # must equal the hash in DATASET_VERSION
```

Determinism: identical seed → byte-identical `items.jsonl` (checked in CI).
The build fails loudly if any QC gate or independent answer verifier fails.

## 2. Regenerate metrics/tables/figures from committed raw records

Raw records (JSONL, one line per item×model) are committed under `results/`.
Analyses never re-query any API:

```bash
# Stage 1 (MMLU-STEM pilot)
stembench report --run results/stage1/S1-P1
# → results/stage1/S1-P1/analysis/{metrics.json, model_table.csv,
#   pairwise_table.csv, figures/*.png}

# Stage 2 (bilingual benchmark; paired cluster-bootstrap analysis)
python -m stembench.analysis_stage2 <run_dir>   # or: stembench analyze-stage2 --run <run_dir>
```

Regenerated tables match the numbers quoted in `reports/` and `paper/` exactly
(their generation commands are recorded in each report header).

## 3. Re-run live evaluations (free tier, budget-aware)

```bash
cp .env.example .env   # fill OPENROUTER_API_KEY / OPENCODE_ZEN_API_KEY (free tier)
stembench run --config configs/stage1_pilot.yaml      # Stage 1
stembench run --config configs/stage2_eval.yaml       # Stage 2 (after build §1)
```

Notes:
- Provider free-tier limits: OpenRouter 20 rpm / 50 requests/day (shared); Zen has no
  documented account cap but per-model upstream saturation occurs. The runner stops
  cleanly at the daily cap and resumes the next day without duplicate calls
  (`n_items` caps new items per invocation).
- Live re-runs at temperature 0 are near-deterministic but NOT guaranteed identical
  (provider-side serving variance); the committed raw records are the canonical
  evidence, and manifests record model IDs, prompt hashes, decoding, git commit.

## 4. Statistical software

All statistics are implemented in `src/stembench/metrics/` on numpy/scipy and unit
tested against hand-computed fixtures and, where applicable, closed-form values
(see `tests/test_metrics_*.py`). No numbers are produced outside these modules.

## 5. Provenance of every published artifact

| Artifact | Generated by | Inputs |
|---|---|---|
| Stage 1 tables/figures | `stembench report --run results/stage1/S1-P1` | committed JSONL records |
| Error annotation files | `scripts/export_error_sample.py` → model-assisted labels → `scripts/merge_error_annotations.py` | incorrect-response records |
| Stage 2 dataset | §1 build command | seed 20260817 |
| Stage 2 tables/figures | `analysis_stage2` | committed JSONL records |
| Rescore (D12/D14 corrections) | `scripts/rescore_records.py <run_dir> --items data/stembench_v1/items.jsonl` | committed records + dataset; every changed record keeps `extra.pre_rescore` |
| Reports/paper | hand-authored text; every numeric claim cites its table | generated tables |

## 6. What cannot be reproduced offline

- Live API behavior (§3) — provider-side; mitigated by committed raw records.
- Human expert validation — not yet performed (release gate; `docs/annotation/`).
